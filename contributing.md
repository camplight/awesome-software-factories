# Contributing

Thank you for helping keep Awesome Software Factories useful and focused. Please read this policy before opening a pull request.

By participating in this project, you agree to follow the [Code of Conduct](code-of-conduct.md).

## Inclusion Criteria

A software factory is a repeatable system that transforms structured intent into deployable or maintained software through automated or agentic workflows spanning multiple lifecycle stages.

Submissions may include:

- End-to-end systems that plan, build, verify, deploy, or maintain software across multiple stages.
- Specification-driven systems that connect structured intent to implementation and verification.
- Business-facing systems that generate and deploy real applications or integrations.
- Modernization systems that transform, migrate, or rebuild existing software through a repeatable workflow.
- Purpose-built software-factory orchestration, control, verification, and execution infrastructure.
- Service-led factories with an identifiable repeatable platform or method that produces working software.
- A small set of directly relevant lists and learning resources.

A core submission must produce deployable or maintained software, own a repeatable workflow across multiple lifecycle stages, and be active, accessible, and sufficiently documented. Purpose-built infrastructure may instead qualify when it directly coordinates, governs, verifies, or operates software-factory workflows.

## Exclusion Criteria

Do not submit:

- Single coding assistants that do not coordinate a broader lifecycle workflow.
- Generic agent frameworks without a specific software-factory workflow.
- Business agents that produce only content, reports, sales activity, or administrative automation.
- Workflow automation products that do not produce deployable or maintained software.
- Ordinary consultancies that merely claim to use AI.
- Unmaintained, archived, deprecated, undocumented, or inaccessible projects.
- Thin demos, unverifiable announcements, and products supported only by secondary promotional coverage.

## Proposing a Change

- Submit one logical addition or removal per pull request where practical.
- Place each item once, under its dominant use case, and alphabetize it within that category.
- Use the project's canonical name and link to its primary project, product, or documentation page.
- Use this entry syntax:

```markdown
- [Name](https://primary.example) - Objective sentence describing the distinguishing software-factory capability and why it is useful.
```

## Evidence and Recommendation

- Cite a primary source that supports the entry's material capabilities. Secondary coverage alone is not sufficient.
- Confirm that the project or offering is currently maintained, documented, accessible, and not archived or deprecated.
- Explain briefly why you personally recommend the item rather than merely asserting that it qualifies.
- Disclose any affiliation, employment, contribution, sponsorship, or self-nomination connected to the item. Disclosure belongs in the pull request, not the list entry.

## Editorial Requirements

- Start descriptions with an uppercase character and end them with a period.
- State concrete capabilities, not vendor slogans.
- Describe why the item is useful or distinctive without ranking it.
- Keep each entry to one sentence wherever possible.
- Use neutral wording and omit star counts, pricing, unsupported autonomy claims, status badges, comparative language, and labels such as "recommended" or "best."
- Keep the existing category structure unless a focused discussion establishes a need to change it.

Meeting the written criteria does not guarantee inclusion. Maintainers may reject an entry that technically qualifies but would weaken the curation, duplicate stronger coverage, or make the list less useful.
